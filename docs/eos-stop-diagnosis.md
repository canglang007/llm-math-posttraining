# 「模型会答但不会停」的完整诊断链

> 2026-11-16 10:35（Asia/Shanghai）

## 一句话

SFT 后模型答完不复述停止、继续编下一道题。根因不是欠拟合、不是 eos 权重不够，
而是**我们用 ChatML 的 `<|im_end|>` 当停止符，而这个 token 在 Qwen3-Base 的
预训练里从未出现**——同时训练又把 Base 原本正确的停止行为（`<|endoftext|>`）
压掉了。两个错误叠加，模型两边都不会。

## 现象

- pilot-v2 checkpoint-200 生成时跑满 512 token，约 2000 字符
- 输出里出现第二个 `####`（下一题的答案），污染判分与采样候选
- 训练侧 loss 看起来正常：0.356 收敛，平均 loss 很低

## 诊断过程（三层，每层都推翻了一个假设）

### 第一层：不是欠拟合——平均 loss 掩盖了单个 token 的失败

对 20 条训练样本做一次 forward，按 token 位置拆 loss（`scripts/diag_eos_loss.py`）：

| 指标 | Base | SFT 200 步 |
|---|---|---|
| assistant 段平均 loss | — | **0.338** |
| `<|im_end|>` 位置 loss | 15.22 | **7.83** |
| `<|im_end|>` argmax 排名 | 14582 | **1982** |
| argmax 命中（greedy 会不会停） | 0/20 | **0/20** |

尾部逐 token loss：`[1e-4, 1e-4, 0.0, 7.83, 0.0]`。

**读法**：答案行之前每个 token 都拟合到 1e-4，唯独收尾那一位是 7.83。
CE 按 token 平均，assistant 段约 64 token，停止符只占 1/64，它的 loss 摊进
平均值只剩约 0.12 —— 所以「平均 loss 已经收敛」是假象。

**结论**：加轮数只会以 1/64 的效率慢慢磨。

### 第二层：加权也救不了——瓶颈不在梯度大小

给停止符位置加权 30 倍（`EosWeightedTrainer`），从 checkpoint-200 续训 40 步：

- loss 曲线 1.92 → 1.93，**平**
- eos_loss 7.83 → 7.77，rank 1982 → **1949**，top-1 仍 **0/20**

同时踩到一个坑：第一次跑 loss 显示 30.7、grad_norm 4.07（正常 0.3）。
原因是新版 transformers 认为模型自己会用 `num_items_in_batch` 做缩放，
不再替我除 gradient accumulation steps，而自定义 loss 把该参数吃掉了，
**梯度被放大 16 倍**（30.7 ≈ 1.92 × 16）。补上 `loss /= gradient_accumulation_steps`
后恢复正常。

**结论**：40 步、20 倍有效信号、rank 几乎不动 ⇒ 这个 token 的瓶颈不在梯度。

### 第三层：真正的根因——对照 `<|endoftext|>` 才看出来

在同一个位置（`#### 答案` 之后），对比两个候选停止符：

| | `<|im_end|>` (151645) | `<|endoftext|>` (151643) |
|---|---|---|
| Base | rank 14577 / 概率 0.0004 | **rank 1 / 概率 56.7%** |
| SFT 旧目标 | rank 1949 / 概率 0.0004 | **rank 151598 / 概率 0** |

两个事实同时成立：

1. **Base 本来就会停**——它自然输出 `<|endoftext|>`，排第 1、概率 56.7%；
2. **SFT 把它压掉了**——rank 1 → 151598，同时新停止符只从 14577 提到 1949。

再看模型在该位置的 top-5：`\tNdrFc` 和几个乱码 token，概率全在 0.0004
——**分布几乎平坦**，不是「偏好错了」，而是「不知道该输出什么」。

为什么 `<|im_end|>` 推不上去：它是 Qwen3-Base 预训练中未使用的特殊 token，
`lm_head` 对应那一行是随机的；而 LoRA 只挂在 attention/MLP，**不含 lm_head**，
无法直接改输出投影。加权只能放大梯度，改不动一个没有意义的输出方向。

## 修复

训练目标改成用模型自己学过的 `<|endoftext|>` 收尾：

- `encode_sft_example` 把 assistant 段最后一处 `<|im_end|>` 替换为 `<|endoftext|>`
  （只换最后一处，system/user 轮次保持 ChatML 原样）
- 推理侧**不需要任何改动**：`resolve_eos_token_ids` 本来就把 base eos(151643)
  包含在内，模型一吐这个 token 就停

## 验证

| 阶段 | 停止符 top-1 | eos loss | dev 10 题 |
|---|---|---|---|
| SFT 旧目标 200 步 | 0/20 | 7.77 | 跑满 512 token |
| 续训 20 步（新目标） | **20/20** | **0.062** | 0.7，抽取失败 0，输出干净收尾 |

生成长度从「跑满 ≈2000 字符」降到 81~568 字符，末尾是干净的 `#### 18`。

## 顺带修掉的下游 bug

即使学会停止，旧模型仍可能「不写标记、直接续写下一题」，此时唯一的信号是
第二个 `####`。`truncate_generation` 增加**答案行锚定**：GSM8K 每题只有一个
`#### 数字` 行，其后内容一律切除。对 1600 条真实采样候选回放：25 条（1.56%）
确实跑到了第二题，91 条文本被清理，判分变化 0、误伤 0。

这一层很重要——抽取取第一个 `####` 只能保住判分，prediction 文本仍是脏的，
会一路带进采样候选、maj@k 投票与 DPO 的 chosen/rejected 配对。

## 面试怎么讲（30 秒版）

> SFT 后模型不会停。我先用一次 forward 把所有 token 的 loss 按位置拆开，发现
> 平均 loss 0.34 但停止符那一位是 7.8——平均值把关键失败盖住了。于是给停止符
> 加权 30 倍，40 步后排名几乎没动，说明瓶颈不在梯度。再做对照：Base 在同一个
> 位置对 `<|endoftext|>` 是 rank 1、56.7%，对我们的 `<|im_end|>` 是 rank 14577。
> 结论是我们的停止符是 Base 没学过的 token，lm_head 那行是随机的，而 LoRA 不含
> lm_head，所以怎么加权都推不上去，同时还把 Base 原本正确的停止行为压掉了。
> 改用模型自己学过的停止符，20 步就到 100% 命中率。

**这题的价值不在于最后那个改动有多小，而在于：三次测量、两次推翻自己的假设、
一次对照实验定位到 token 层面。**
